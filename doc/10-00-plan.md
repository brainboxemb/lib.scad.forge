# Forge plan

## Purpose

Forge is the small shared OpenSCAD modeling layer for the BrainboxEmb SCAD
portfolio. Its goal is to make recurring modeling intent easier to read and
review without replacing normal OpenSCAD.

The fuller rationale for Forge and each functional area lives in
[30-00-specification.md](30-00-specification.md).

## Scope

Forge owns generic modeling mechanics. Project/product geometry, mechanical
interfaces, fit rules, manufacturing tolerances, slicer settings and
domain-specific hardware meaning stay in their owning repositories.

## Working method

For normal Forge work:

1. start here for scope, sources, current focus and roadmap;
2. read [30-00-specification.md](30-00-specification.md) to understand why the
   affected capability exists and what it is intended to achieve;
3. read [40-00-design.md](40-00-design.md) for the library architecture;
4. follow any detailed-design link for the affected functional area;
5. read [50-00-verification.md](50-00-verification.md) before changing tests or
   verification evidence;
6. update the structured API comments beside the public `.scad` API when a
   public call, usage rule or deprecation changes.

Do not add a Forge helper merely to increase Forge usage. Prefer the smallest
construct that makes the design intent clearer than native OpenSCAD.

## Current focus

The current cross-project context is `brainboxemb.meta` Migration 011.

Forge repository/tooling integration issue #32 is complete and qualified on exact
main. The current owner step is the `v0.3.1` patch release candidate for that
integrated baseline.

Issue #30 (`fg_overlap_mm()` retirement) remains a separate Forge API decision
and is intentionally not part of `v0.3.1`.

Resolution context continues to use canonical `fg_res_scope()`.
`fg_res_apply()` remains deprecated while maintained consumers migrate.

## Roadmap

Near-term:

1. publish the Migration-011 tooling integration as `v0.3.1`;
2. keep issue #30 separate until Forge API cleanup is intentionally resumed;
3. migrate known BrainboxEmb `fg_res_apply()` consumers;
4. decide the later pre-1.0 removal boundary separately from this tooling release.

Release-boundary/version-selection ambiguity is tracked cross-project in
`brainboxemb.meta` issue #155.



Near-term:

1. retire `fg_overlap_mm()` through issue #30;
2. release v0.4.0 with `fg_res_scope()` canonical and `fg_res_apply()`
   deprecated;
3. migrate known BrainboxEmb `fg_res_apply()` consumers;
4. remove `fg_res_apply()` in the following pre-1.0 minor release.

The intended cadence remains deprecation in v0.4.0 and removal in v0.5.0. If
release numbering changes before publication, preserve the policy of one
compatibility release followed by removal.
